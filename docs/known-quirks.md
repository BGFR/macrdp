# Known behavioural quirks

- **Non-US keyboard layouts (`--keyboard-layout`) translate server-side via UCKeyTranslate and post Unicode — they do NOT switch the Mac's input source.** Built 2026-06-16. RDP clients send PS/2 *positional* scancodes, not characters; `input.rs` maps those to macOS virtual keycodes (also positional) and macOS turns a keycode into a character using **the Mac's active input source** — so a non-US client on a US-configured Mac types the wrong letters. The chosen fix (`src/keyboard_layout.rs`) resolves the requested layout to a macOS `UCKeyboardLayout` (via `TISCreateInputSourceList` on the input-source id, falling back to `TISCopyInputSourceForLanguage`) and, for each ordinary typing key, calls `UCKeyTranslate(keycode, modifier-state)` → Unicode, which `input.rs::key` posts as a string event (keycode 0 + `set_string_from_utf16`, the same mechanism as the RDP Unicode-keyboard path). **The alternative — `TISSelectInputSource` to switch the Mac's active layout — was explicitly rejected**: it would change the *local* Mac's keyboard while connected (visible/disruptive to a local user in mirror mode). Load-bearing details: (1) **Only the contiguous ANSI block is translated** — `is_translatable_keycode` = vk ≤ 0x32 **minus Return (0x24), Tab (0x30), Space (0x31)**; those three plus everything ≥0x33 (arrows, F-keys, keypad, editing) must stay on the keycode path so they behave as *keys*, not literal characters. (2) **Cmd/Ctrl combos are NOT translated** (gated on `!has_cmd() && !has_ctrl()`) so app shortcuts (Cmd+C, Cmd+Q) keep firing as keycodes; Shift/Option(AltGr)/Caps ARE folded into the translation (Option→AltGr chars like €). (3) **Dead keys compose** because `dead_key_state` persists across calls — a dead key returns `Some("")` (swallowed; nothing posted) and the accent lands on the next keystroke. (4) **The key-up is swallowed too** for translated keys — Unicode string events have no release side, so posting a bare key-up would desync the focused app. (5) The Unicode event is posted with **no modifier flags** (the shift/option were already baked into the character) so the app doesn't re-apply them. The KLID arrives in the GCC Client Core Data (`keyboard_layout: u32`, same place the desktop-size feature reads), so **auto-detecting the layout from the client is a natural follow-up** (acceptor plumbing like `honor_client_desktop_size`); today it's a `--keyboard-layout` flag / `KEYBOARD_LAYOUT` config key. Verified: US-layout translation unit-tested end-to-end (A→a, Shift→A, Caps→A, 1→1, Shift+1→!) and French resolves live on macOS 26. The layout must be installed on the Mac (we pass `include_all=1` so even non-enabled bundled layouts resolve).
- **Client-resolution auto-adopt (default; `--no-client-resolution` to opt out) MUST live in the acceptor — the Confirm Active capset cannot reveal the client's requested size.** Built 2026-06-12 to kill mstsc's client-side rescale (typing latency + H.264 audio drift when the served resolution ≠ the client display's). The client's own requested resolution exists in exactly one place: the GCC **Client Core Data** `desktop_width/height` of the MCS Connect Initial. The tempting alternative — upstream's `RdpServerDisplay::request_initial_size`, fed from the client's Confirm Active bitmap capset — is a dead end for detection: conformant clients **overwrite their desktop size with the server's Demand Active values and echo those back** (verified in FreeRDP's `rdp_apply_bitmap_capability_set` source AND live: sdl-freerdp `/size:1024x768` echoed our 1512×982; mstsc follows the same `desktopResizeFlag` contract). Worse, upstream `ironrdp-acceptor` parses the Client Core Data and discards everything but the early-capability flags, and Demand Active is sent *inside* `accept_finalize` — before any server-side code can react. So: `vendor/ironrdp-acceptor` (new fork, divergence log inside) gains `honor_client_desktop_size` — in `BasicSettingsWaitInitial` it adopts the client's core-data size (sanity band 200..=8192 per MS-RDPBCGR) into `desktop_size` + the server Bitmap capset BEFORE Demand Active, so the session is negotiated at the client's resolution from the start with **no deactivation-reactivation resize**. (A reactivation-based variant — emit `DisplayUpdate::Resize` as the first update — was built first and discarded: it cost an extra full reactivation per connect and still couldn't *detect* anything for echo clients.) The vendor server forwards the flag (`RdpServer::set_honor_client_desktop_size`, divergence 9); `CaptureDisplay::request_initial_size` then adopts the echoed size into the process-wide `SharedDesktopSize` (capture.rs) that capture, `input.rs` mouse scaling, and the `h264.rs` surface/encoder all read — input reads per-event, h264 pins dims per connection in `setup_locked`. Costs are exactly the documented non-native-capture trade-offs below (full-frame legacy updates; on aspect mismatch the picture is **letterboxed/pillarboxed by default** to preserve the Mac's aspect ratio, `--stretch` opts into fill-and-distort — see the scaling note); that's the accepted deal — the prior workaround was passing `--width 1920 --height 1080` manually. Verified live with sdl-freerdp at 1024×768 (legacy) and 1280×800 + 800×600 (H.264/EGFX, fresh surface per connection, acks flowing); mstsc verification pending a real Windows client. Disabled automatically when `--width`/`--height`/`--hidpi`/`--virtual-display` pin a size.
- **Server-side scaling forces full-frame updates; aspect handling is letterbox-by-default on the auto-size path, stretch otherwise.** Capturing at a configured size ≠ the Mac's native size makes SCK scale internally, and SCK's dirty-rects then come in *source* (native) coords (clients that strictly respect tile coordinates render a black canvas with only the cursor sprite — mstsc/RemoteFx is the worst offender). `capture.rs` works around that by detecting the mismatch up front and skipping dirty-rect emission (full BitmapUpdate every tick — the upstream encoder's framebuffer diff still keeps unchanged-region cost low). For the aspect dimension there are two modes, both with `scales_to_fit=true`:
  - **Letterbox/pillarbox (default on the auto-size path, i.e. client-resolution auto-adopt with no `--stretch`):** `preserves_aspect_ratio(true)` — SCK fits the Mac into a **centered** sub-rect of the output and pads the rest with black bars, so the picture isn't distorted. `input.rs::move_to` then maps client coords into that centered content rect (clicks in the bars clamp to the nearest edge) via the pure, unit-tested `map_client_to_display`; the shared `SharedDesktopSize.letterbox` flag tells it which mode is live. **Verified 2026-06-15 on macOS 26** by dumping a captured frame: a 1512×982 Mac → 1920×1080 client produced a centered 1663×1080 image with **exactly 128 px bars each side** (= `(1920−1663)/2`), matching the input math — so clicks align. (No inverse-`preservesAspectRatio` surprise on 26; if a future macOS flips it, the bars will land on the wrong axis and clicks will skew — re-dump a frame to check.)
  - **Stretch/fill (`--stretch`, or any explicit `--width`/`--height`):** `preserves_aspect_ratio(false)` — source stretches to fill the whole output (no bars), with the old caveat of non-uniform scaling on aspect mismatch (e.g. 16:10→16:9 ≈ 13.5% vertical compression) and `input.rs` mapping linearly across the full frame.

  Cost at non-native sizes either way: higher bandwidth (full frames) and, on **mstsc with `--enable-h264`**, the scaling amplifies its trailing-frame presentation lag (see the flush-burst note) — a Mac whose native resolution already matches the client serves 1:1 with no scaling and is markedly snappier (confirmed live: a 1512×982 MacBook Pro lags into a 1080p mstsc session while an M1 mini natively driving 1920×1080 does not). Prefer native if you can.
- **No server PointerPosition forwarding (intentional).** mstsc and Microsoft Remote Desktop local-predict the cursor from the user's mouse input; any `PointerPositionAttribute` PDU we send arrives one encode-plus-network round-trip late and snaps the cursor back to a stale position on fast moves. The current design (`poll_shape` only, `poll_position` defined but unwired) is deliberately the right one for all interactive use. *Do not* simply wire `poll_position` up — that's the bug, not the fix. The only thing this design misses is Mac-side *programmatic* cursor moves (an app calling `CGWarpMouseCursorPosition`, rare); fixing that properly requires emitting position only when the Mac cursor diverges from where the last RDP mouse event left it and enough time has passed since that event, which needs shared state between `input.rs` and `cursor.rs`.
- **Legacy codec mismatch with the macOS client (only without `--enable-h264`).** In the legacy bitmap path, Microsoft Remote Desktop / Windows App on macOS offers only NSCodec while the server advertises RemoteFx/QOI, so they fall back to raw/RLE BitmapUpdate — works, but bandwidth-heavy. With `--enable-h264` that same client negotiates AVC420 over EGFX and renders H.264 (verified), which is far better — prefer it for the macOS client.
- **EGFX capability parsing must tolerate unknown versions (Windows App fix).** Windows App for Mac (`com.microsoft.rdc.macos`) advertises an EGFX capset version that older ironrdp_egfx didn't recognize; the `CapabilityVersion::try_from` returned `Err` on it, which the CapabilitiesAdvertise decode propagated as a *fatal* error — killing the whole connection during negotiation, before the AVC-vs-legacy fallback could run. So `--enable-h264` made Windows App unable to connect at all (it connects fine without). Fixed in upstream ironrdp_egfx via PR #1298 (merged 2026-05-25); we pin the ironrdp rev at-or-after `67f3c63` and the previously-vendored `vendor/ironrdp-egfx/` was dropped.
- **H.264 wire format must be Annex-B, and mstsc retains EGFX surfaces.** Two hard-won facts behind `src/h264.rs` (`--enable-h264`): (1) the AVC420 payload must be **Annex-B** (start codes + in-band SPS/PPS) — Microsoft's decoder gives zero frame-acks for length-prefixed AVCC, so the default is Annex-B (`MACRDP_H264_LENGTH_PREFIXED=1` flips it for ironrdp-decoder interop). (2) **mstsc retains EGFX surfaces by id for its whole process lifetime** (across reconnects and even macrdp restarts) and no-ops a `CreateSurface` for an id it already holds → frames decode into a stale surface → black screen + live cursor on reconnect. We use upstream's auto-allocated surface id and **document the limitation** rather than fight it: the reliable recovery is to fully close and reopen the mstsc window, which clears its surface cache. **Do NOT try to fix this with `DeleteSurface`** — deleting a surface mstsc doesn't currently hold (or one mapped to the output) breaks its GFX channel entirely (no acks, then disconnect); confirmed twice. **A fresh-unique-id-per-session workaround was tried and removed** (it lived in a vendored `create_surface_with_id`): on mstsc it only *unreliably* avoided the blank — sometimes the desktop drew, sometimes not — and since the reliable recovery (close+reopen mstsc) is identical with or without it, it wasn't worth a permanent upstream divergence. FreeRDP (with H.264) has none of these quirks — it renders and reconnects cleanly, which is how we proved the server output is spec-correct. The residual mstsc reconnect blank is therefore a documented client limitation, not a server bug.
- **mstsc holds a ~2-frame AVC420 presentation buffer; the last change before a pause needs trailing "flush" frames (`--flush-frames`, in `capture.rs`).** mstsc only *presents* an H.264 frame once ~2 more frames arrive behind it, so on a static screen the last change (the final keystroke before you pause, a window-to-front) strands in that buffer until something else moves or the periodic keyframe lands — the "typing follows the keyframe" lag. The trap: **ScreenCaptureKit stops delivering frames when nothing on screen changes** (idle samples have no content and are skipped at `capture.rs`), so there is no continuous stream to push the buffer through — raising `--fps` alone does *not* fix it (it only shrinks the per-frame interval). The fix is a **bounded flush-burst**: after each EGFX-accepted frame, `next_update` stashes the BGRA (reused buffer) and arms a counter; its SCK stream-wait is wrapped in `tokio::time::timeout(frame_interval, …)`, so when SCK goes idle the timeout fires and we re-submit the stored frame as a cheap skip-P-frame, `--flush-frames` times (default 4; mstsc needs ≥2; **0 disables**). That drains the buffer within ~2 frame intervals (~33 ms at 60fps), then the stream goes quiet — no always-on cost, and the legacy bitmap path is untouched (the counter only arms on the EGFX path). **Do NOT "fix" this by reinstating idle-frame suppression or relying on a continuous always-on stream** — SCK won't feed one, and suppression strands the trailing frame again (tried and reverted). FreeRDP/Thincast present each frame immediately and need none of this. Verified on M1; periodic `--keyframe-interval` default is 2 s (it self-heals garbled frames but, with the flush-burst, no longer governs typing latency).
- **Resizing/moving the mstsc window drifts audio late — H.264-only (`--enable-h264`).** With H.264, EGFX video frames and the RDPSND audio waves share the *same socket writer* — a single `SharedWriter` (`Rc<Mutex<..>>` over the one TCP connection) cloned per task. Audio rides its own dedicated `mpsc` channel + `dispatch_audio` task (it was carved out of the unified `ServerEvent` channel), but every `audio_writer.write_all` still has to acquire that one shared socket lock — the same lock the EGFX path holds while writing a frame. Legacy bitmaps don't contend the same way (dirty-rect, intermittent, default 15 fps, coalesced through `dispatch_display`), which is why the legacy path is immune. When mstsc freezes the socket during a window resize/move/fullscreen-toggle, `write_all` blocks on the large queued video frames; wall-clock keeps advancing while no audio ships, so the cross-batch audio-lag model in `vendor/ironrdp-server` (`audio_shipped_ms` vs `audio_clock_start`) sees its buffer projection go *negative*, reads it as "client starving," and ships the entire stale backlog late — bloating the client's playback buffer. Each stall adds more negative credit, so without intervention the wave-drop logic stops firing and audio gets *progressively* more delayed the more you resize. Fix (in `dispatch_audio`'s task-local lag loop): when `real_elapsed - audio_shipped > 300 ms` the writer clearly stalled and the queued waves are stale, so resync `audio_shipped_ms` to live; the existing drop-oldest cap then trims the backlog to one `MAX_LAG_MS` (200 ms) of the freshest waves. For a live stream, dropping stale audio is always right — never replay it late. EGFX frames themselves are *not* dropped in dispatch (H.264 inter-frame coding forbids it; they're bounded capture-side by frames-in-flight). FreeRDP/Thincast don't freeze the socket on resize and never showed this. See the `vendor/ironrdp-server` note for the divergence layering (this resync is local-only, distinct from the merged keep-newest PR #1276).
- **Honoring `SuppressOutput` is required to avoid input-lockout on minimize→refocus — but three arming gates are also required, or mstsc freezes on connect / reconnect / stutters under heavy local CPU/IO.** Reported + fixed 2026-05-26 (v0.5.47, debounce + mute-on-minimize landed in v0.5.48). Original bug: minimize mstsc for several minutes with H.264 video flowing → refocus → desktop frozen, audio skips, video speeds up to catch up. Root cause: vendor server was logging `SuppressOutput` as `Unexpected share data pdu` and ignoring it; we kept streaming 60 fps of EGFX frames into a minimized client, which accumulated them, and on refocus mstsc had to chew through the backlog before it could present the current frame — its input dispatch was busy the whole time, ~several seconds of total UI lockout. Fix: vendor server pattern-matches `SuppressOutput` / `RefreshRectangle` and toggles a shared `Arc<AtomicBool> display_suppressed` (exposed via `set_display_suppressed_handle`); `capture.rs::next_update` checks the flag and short-circuits SCK pull + encode + ship while it's set; on the true→false edge a one-shot IDR keyframe is forced so the client resumes from a clean reference frame. **Three arming gates are non-obvious and load-bearing:** (1) **first-EGFX-frame gate** (`first_egfx_frame_sent` in `ScreenCaptureUpdates`) — mstsc's normal connect handshake includes a `SuppressOutput { None }` *before* its display surface is fully initialized; honoring it then leaves mstsc with a half-init'd surface that doesn't recover on un-suppress and the desktop never paints. FreeRDP doesn't issue suppress during connect and was never affected, which is why blanket honor "worked on FreeRDP." Gate the gate so it's only respected after the first EGFX-accepted frame ships. (2) **per-connection reset of the flag** (in `ScreenCaptureUpdates::start`) — the `Arc<AtomicBool>` is owned by the server and survives across disconnect/reconnect; if the previous session ended with it `true`, the *next* connection arms its first-frame gate, immediately reads the stale `true`, and freezes the new session. Reset to `false` at the top of every `start()` call. (3) **per-reader debounce (`SUPPRESS_DEBOUNCE = 1 s`, identical in `capture.rs` and `audio.rs`)** — under heavy local CPU/IO (cargo build, big disk I/O) mstsc emits transient `SuppressOutput { None }` → `RefreshRectangle` pairs tens of ms apart to throttle the server when its receive queue grows. Reacting to those rapid flaps thrashes both the video gate and the audio mute, producing audible stutter and visible video hiccups even though no real minimize occurred. Each reader maintains a local `Option<Instant>` "first observed suppress=true" timestamp and only engages the gate once `elapsed >= SUPPRESS_DEBOUNCE`. Real minimizes (seconds-to-minutes) cross that threshold easily; backpressure flaps don't. Don't remove any of the three gates without re-testing first-connect, reconnect-after-disconnect, long-minimize, AND cargo-build-while-watching-YouTube on mstsc. Mute-on-minimize is default-on (`--no-mute-on-minimize` to disable) and uses the same shared flag + same debounce so audio and video stay coherent through transients.
- **Minimizing mstsc for minutes then refocusing → audio plays back 1s+ late, and we can't see it from the server side.** Reported 2026-05-26. When mstsc is minimized while RDPSND audio keeps flowing (e.g. YouTube playing on the Mac while the user does other Windows work), Windows' audio mixer (`audiodg.exe`, a separate process) appears to throttle playback while continuing to drain mstsc's network buffer; on refocus, the buffered backlog plays out — audio lags by however much accumulated. **`WaveConfirm` is not a usable signal for this** — investigated 2026-05-26 by surfacing every confirm via `RUST_LOG=ironrdp_rdpsnd=debug`. Confirms flow continuously through minimize at full ~46/sec rate (one per ~21 ms wave), with no gaps or slowdowns. That means mstsc emits `WaveConfirm` on *arrival/queue* into its dispatch (it has received and forwarded the wave to audiodg), not on *playback completion through speakers*. The actual buffering happens downstream in audiodg, which the RDP stack does not observe. A server-side wave-confirm tracker (the obvious "detect client playback lag" design) would see all confirms arriving fine and never trip its drop logic; it cannot fix this. **Do NOT try to fix this with a `WaveConfirm`-based playback tracker** — verified dead-end. The two realistic options if this becomes worth fixing: (a) heuristically throttle wave emission while mstsc has sent `SuppressOutput` (correlates with minimize but not 1:1 — see the `Unexpected share data pdu` warnings in logs); (b) accept as a Windows audio-mixer behavior we cannot see from RDP and document the limitation (current choice).
- **Cursor sprite shape is process-global on macOS, not per-display.** `NSCursor::currentSystemCursor()` reflects whatever the foreground application set in *this process*'s perspective, not "the cursor on display X." When `--virtual-display` is active, the RDP client sees the cursor shape that whatever app is foreground locally has set (typically the arrow), regardless of what an app on the virtual display might want. Probably fine in practice — the cursor *position* on the virtual display is correct because `input.rs` translates RDP coords by the vdisplay's origin in global space; only the visual shape is shared. Fixing this properly needs a per-display NSCursor query, which AppKit doesn't expose.
- **`--virtual-display` on mstsc: large legacy frames are strip-split, a release build matters, and the cursor is warped home on disconnect.** Verified 2026-06-02 against remote mstsc. One gotcha plus two fixes: (1) **Legacy big-frame blank on mstsc — FIXED by strip-splitting.** A virtual display is captured 1:1, so `force_full_frame` is *false* — the full WxH paint is sent once on the first frame, then dirty-rects. The bitmap encoder (`vendor/ironrdp-server/src/encoder/bitmap.rs`) packs that whole rect into ONE update PDU (one RLE rectangle per ~`65535/(w*4)` rows), and mstsc has a per-update size/rect-count limit: it renders a single ~1280×720 (≈0.9 MP, ~60 rects) update but DROPS a 1920×1080 (≈2.1 MP, ~135 rects) one, so the desktop never painted (only the ticking-clock dirty-rect rendered → "almost blank, only the menu-bar clock visible"). FreeRDP (tolerant) rendered either. Disambiguated by testing: a 1280×720 vdisplay renders on mstsc, 1920×1080 doesn't — i.e. it's the *size*, not once-vs-repeated. Fix: `capture.rs::split_strips` splits any emitted rect into horizontal strips ≤ `MAX_BITMAP_UPDATE_PIXELS` (= 1280×720, the proven-good size) so each becomes its own smaller, renderable update. Verified: 1920×1080 legacy vdisplay now renders the full desktop on mstsc. (`--enable-h264` is still preferable for bandwidth/quality, but legacy no longer blanks.) (2) **Debug builds make mstsc reset.** `cargo run` (unoptimized) encodes ~400 ms/frame; that stalls the socket and mstsc resets the connection right after the first EGFX frame ("Connection reset by peer"). A release build (`cargo build --release`, ~20× faster encode) holds the connection and renders cleanly. Always test mstsc on a release build. (3) **Cursor-stranding fix.** During a vdisplay session `input.rs::move_to` posts the cursor into the virtual display's slot of the global coordinate space (off every physical panel). The vdisplay outlives the per-connection capture object, so on disconnect the local cursor was stranded and unusable until macrdp exited. Fixed: `ScreenCaptureUpdates` carries a `warp_cursor_home` flag (set when `--virtual-display`) and on `Drop` (per-connection, fires on disconnect) `CGDisplay::warp_mouse_cursor_position`es the cursor to the primary physical display's center. Primary-capture path is unaffected. Signal-exit needs no warp (the OS reaps the vdisplay → cursor reparks).
- **mstsc gates Win-combos by full-screen by default.** mstsc → Local Resources → Keyboard → "Apply Windows key combinations" defaults to "Only when using the full screen", so a windowed mstsc session eats `Win+Tab` (the Cmd+Tab we want to forward) locally as Task View — macrdp never sees the press. The #1 false-positive when debugging "Cmd+Tab doesn't work" is the user being windowed. Set it to "On the remote computer" or go full-screen. `xfreerdp` is more permissive by default and a useful cross-check.
- **Symbolic-hotkey dispatcher needs kernel HID; CGEventPost can't wake it.** WindowServer's internal Cmd+Tab / Cmd+Space / Cmd+Shift+3/4/5 / Mission Control dispatcher only fires on kernel-injected HID events. User-space CGEventPost cannot trigger it regardless of source state or tap location. A `src/virtual_hid.rs` module that registered a virtual USB-style HID keyboard via `IOHIDUserDeviceCreate` was tried for this and reverted — didn't unblock the dispatcher (likely needs entitlements / signing we don't have) and added a parallel scancode-mapping table to maintain. The current design instead reimplements each symbolic combo in user space (`cycle_apps` via AX, `invoke_spotlight` via osascript, `screencapture` via the binary). Do not resurrect IOHIDUserDevice without new evidence.
- **`CAN_LOCK_CLIPDATA` is required for reliable Windows→Mac file paste.** Without it advertised in `MacCliprdrBackend::client_capabilities`, the upstream cliprdr crate's `send_lock` short-circuits (returns None) and Windows Explorer is never told when we're done with a `FileGroupDescriptorW` it gave us. Two visible symptoms on mstsc, both caused by the same missing protocol contract: (1) a rapid follow-up Ctrl-C in Windows after a successful paste is silently dropped — no new FormatList reaches the Mac, so the pasteboard keeps the previous file's URL and Cmd-V re-pastes the prior file. (2) Large downloads (multi-hundred MB) get `CB_RESPONSE_FAIL` partway because the source app decides the descriptor isn't being held and releases it mid-stream. Adding `CAN_LOCK_CLIPDATA` lets cliprdr auto-issue LockData on incoming file-list FormatList and UnlockData on supersession/timeout — verified to fix both symptoms. Cap is essentially free; mstsc/freerdp both negotiate it. *Do not* remove the cap without a compelling reason.
- **Lazy paste (default; `--no-lazy-paste` to opt out) runs the byte fetch on the user's Cmd-V; the fetch competes with the RDP session for the same socket.** The lazy path's `relinquishPresentedItemToReader:` callback runs during interactive use (the user is staring at the screen, expecting responsiveness), and the `FileContentsRequest` chunks ride the same TCP connection as EGFX video + input. We cap parallelism at `LAZY_PARALLEL_CHUNKS = 2` (vs eager's 8) so the inbound socket pressure stays low and mouse/keyboard remain usable during a multi-hundred-MB paste. Raising it would speed downloads but visibly stutter input — verified on real mstsc. The trailing edge of a large paste can also stutter briefly while Finder finalizes (APFS sparse-block materialization + Finder post-validation); not currently mitigated and probably not worth chasing.
- **Windows shell extensions can silently block specific files from CLIPRDR.** When a file has an extension owned by a shell extension (commonly archive tools — 7-Zip / WinRAR / built-in Compressed Folders for `.zip`, `.gz`, `.bz`, `.bz2`, `.7z`, `.rar`, `.tar`), the extension can intercept Explorer's clipboard handling so the FormatList that mstsc forwards either has no `FileGroupDescriptorW` at all (the more common case — `cliprdr=debug` shows `Expiring active locks due to clipboard change (new FormatList received)` with no following `Received FileGroupDescriptorW` line) or never gets sent. To mitigate the surprising-paste UX (Mac pasteboard would otherwise retain the previously-pasted Windows file's URL and Cmd-V in Finder would silently paste the wrong file), `MacCliprdrBackend::on_outgoing_locks_expired` clears NSPasteboard whenever Windows transitions clipboard state without sending a file descriptor — Cmd-V then beeps clearly. Renaming the file to a neutral extension (`.bin`) bypasses the shell handler and copies fine. Not fixable server-side beyond the auto-clear.
- **AAC audio (`--enable-aac`) is raw access units with `cbSize=0`, and the AudioToolbox pull loop has an end-of-stream trap.** Four hard-won facts behind `src/aac.rs`: (1) **Wire format.** The `WAVE_FORMAT_AAC_MS` (0xA106) payload over RDPSND is **raw AAC-LC access units** — object type 2, 1024 frames/AU, NO ADTS/LATM headers and NO in-band AudioSpecificConfig. The AAC `AUDIO_FORMAT` is advertised with `cbSize=0` (no HEAACWAVEINFO blob); the decoder derives its config from the WAVEFORMATEX rate/channels. Verified against FreeRDP's server (`server/common/server.c` advertises 0xA106 with `cbSize=0`; `dsp_fdk_impl.c` configures fdk-aac `AOT=2`, `TRANSMUX=0`). AudioToolbox's `kAudioFormatMPEG4AAC` encoder emits exactly this, so the magic cookie / ASC it can produce is intentionally never sent. (2) **The EOS trap.** `AudioConverterFillComplexBuffer`'s input proc returning `noErr` with zero packets is read by AudioConverter as *end-of-stream* — after the first batch the converter refuses all further input and audio dies after ~3 packets. The proc must instead return a **non-zero sentinel status** (`INPUT_EXHAUSTED`) to mean "no more data this batch"; `encode` treats that as a clean break, leaving the converter's internal <1024-frame remainder buffered for the next call. (3) **The vendored audio-lag model is byte-based and had to learn duration.** `vendor/ironrdp-server`'s `dispatch_audio` task converts each wave's *byte length* to ms via `BYTES_PER_MS = 176.4` (PCM-specific). A ~120-byte AAC AU is ~23 ms, so that math reads the projected client buffer as near-empty and silently disables the drop-oldest/resync lag control. Fix: `AudioWave` gained a third field `Option<f64> duration_ms`; AAC passes `Some(1024/44100*1000 ≈ 23.22)`, PCM passes `None` (unchanged). See vendor divergence (8). (4) **~40–50 ms priming latency** is why it's opt-in — PCM stays the LAN default. Clients without an AAC rdpsnd decode path fall back to PCM automatically because we advertise both, AAC first, and `start()` picks the first mutually-supported format. (MS-RDPEA notes AAC implies unreliable-UDP DVC transport, but RDPSND over the static TCP channel carries AAC fine — FreeRDP's server does the same.) **Client-support matrix (verified 2026-05-30).** Whether a FreeRDP-family client decodes AAC is build-dependent, and it's NOT just the `WITH_FDK_AAC`/`WITH_FAAD2` flags: `freerdp_dsp_supports_format` first delegates to the **FFmpeg DSP backend** when `WITH_DSP_FFMPEG=ON`, and there AAC is the *only* compressed RDPSND codec NOT filtered out (`ffmpeg_codec_is_filtered` hard-drops MP3/GSM/ADPCM/G.711 unless `WITH_DSP_EXPERIMENTAL`, but returns false for `AV_CODEC_ID_AAC`). So a stock Homebrew `sdl-freerdp` 3.26.0 — `WITH_FDK_AAC=OFF WITH_FAAD2=OFF` but `WITH_DSP_FFMPEG=ON WITH_FFMPEG=ON` — **advertises AAC and decodes our raw AUs cleanly via FFmpeg** (live test: server `use_aac=true client_formats=2`; client log `Opening device with format WAVE_FORMAT_AAC_MS [backend WAVE_FORMAT_PCM]` then `rdpsnd_treat_wave` on every ~280-byte AU with zero `aacDecoder_DecodeFrame failed`). The feared raw-AU "needs ASC as extradata" wrinkle did not materialize — FFmpeg's AAC decoder handled it. By contrast the **Thincast** build tested advertised only PCM (`client_formats=1`) — its rdpsnd path has no AAC decoder — so it (correctly) falls back to PCM; that's a Thincast build limitation, not a server bug. mstsc decodes AAC natively. Practical upshot: AAC is effectively the only non-PCM RDPSND codec any modern FreeRDP build will take, and we already advertise it; there is no other compressed format worth adding for the fallback clients. (Test note: on macOS use `sdl-freerdp`/`wlfreerdp`, NOT `xfreerdp` — the latter is the X11 client and fails `pre_connect` with no `$DISPLAY`.)
- **RDPSND `wFormatNo` indexes the CLIENT's format list, not the server's — latent bug exposed by AAC.** `start()` returns the `wFormatNo` stamped onto every Wave2 PDU, and the client resolves the wave's codec as `ClientFormats[wFormatNo]` — an index into the *Client Audio Formats PDU the client sent back*, which is its supported subset of our server list, compacted in server order. FreeRDP/Thincast hard-reject `wFormatNo >= NumberOfClientFormats` (`rdpsnd_recv_wave2_pdu` / `rdpsnd_recv_wave_info_pdu`) and drop the wave silently — no audio. For years `audio.rs::start()` returned the *server*-list index and it worked only because we advertised a single format (server idx == client idx == 0). The moment `--enable-aac` made the list `[aac, pcm]`, a PCM-only client (Thincast advertised `client_formats=1`) got `wFormatNo=1` for PCM's *server* slot while its own list had PCM at index 0 → `1 >= 1` → every wave rejected → silent. mstsc happened to keep working because it lists AAC at index 0 in both. Fix: choose the format by server preference (AAC-first, so we know what to encode), then return that chosen format's position in `client_format.formats` (the client list). **Do NOT revert to the server-list index** — the old code comment claiming "wFormatNo indexes the server list, client-list index causes wrong pitch" was a misdiagnosis: wrong pitch only happens if you pick the format by scanning the *client* list first and matching loosely (you can select a different rate than you encode). Picking via server preference and *then* translating that exact format to its client-list slot is correct for both mstsc and FreeRDP, because the index always points at the format actually being sent. Verified: Thincast/FreeRDP `use_aac=false` PCM fallback was silent before, plays after.
- **HiDPI / Retina capture (`--hidpi`) — what's load-bearing and what's client-bound.** Established 2026-05-30 building the feature. (1) **SCK delivers backing pixels cleanly.** Setting `SCStreamConfiguration` width/height to the display's backing size (`CGDisplayMode::pixel_width/height`, e.g. 3024×1964) makes SCK deliver a full crisp backing-resolution buffer with the existing `scales_to_fit(true)`/`preserves_aspect_ratio(false)` config — `pb_width/pb_height` come back at 3024×1964, not downscaled. A prior (2026-05-17) "blank screen" attempt did NOT reproduce; current screencapturekit 2.1 handles it. Use `display_mode().pixel_width/height` for backing, NOT `CGDisplay::pixels_wide/high` (canonical mode = points on many configs). (2) **Input is resolution-agnostic for free** — `input.rs::move_to` scales RDP coords against `CGDisplay::bounds()` *points*, not the framebuffer, so doubling the framebuffer self-corrects; no input change needed. (3) **`force_full_frame` must treat backing as native** — it compares the configured size against `display.width()` (SCK points); a backing-size capture (3024 ≠ 1512) would wrongly force full frames + warn. Fixed to accept EITHER the point size or the backing size as a 1:1 native capture (dirty-rects stay valid; the EGFX/H.264 path submits full frames regardless so it's unaffected either way). (4) **Do NOT scale the cursor.** SkyLight's `SLSGetGlobalCursorData` already returns the pointer at backing/physical pixels (≈28 px on Retina) and RDP clients render pointer bitmaps at 1:1 device pixels regardless of session resolution — so the same bitmap is correct at points OR backing. An attempt to upscale it by the backing/points ratio made the pointer 2× too big; reverted. An *opt-in* `--cursor-scale` multiplier (default `1.0` = native size, no resize) was later added for comfort: some clients draw the pointer at 1:1 device pixels while upscaling the desktop image to their window, which makes the native-size pointer look small, so bumping it (e.g. `2.0`) enlarges the bitmap **and** its hotspot together via an alpha-weighted area resample (`cursor/mod.rs::scale_cursor`) — the hotspot stays exact at any value. An auto-scale-to-points *default* was tried during this work and rejected: the user preferred native size, and a separately-reported Retina "cursor shrank / hotspot off" turned out to be a **stale mstsc pointer cache** (cleared by reconnect / close+reopen), not a server scaling bug — so the default still does NOT scale. (5) **The lag is the client, not the server.** VideoToolbox encodes 3024×1964 in ~10 ms/frame (99 fps of headroom, under the 16.67 ms/60fps budget) — the server keeps up and doesn't drop frames. But **mstsc decodes 4× the pixels per frame and, with its documented 2-frame presentation buffer (now of 4×-bigger frames), feels laggy at HiDPI**; Thincast/FreeRDP decoders stay snappy. This is a client characteristic, documented not fixed — which is why `--hidpi` is opt-in and best paired with a capable client. A latent server lever exists (the per-frame ~9 MB NV12 `CVPixelBufferCreate` in `videotoolbox.rs::encode_frame` could be pooled to shave a few ms) but won't change the client-side floor.
